# Changes, 11 Nov 2026

GPS error handling before tuning the controller in the field. Four changes,
one test file. Nothing here has driven yet - it is all proven in simulation
against the real controller code (`test_gps_handling.py`, 19 tests).

---

## 1. One definition of the antenna geometry - and a 1.44 m bug

New `vehicle.py` holds `ANTENNA_OFFSET_M` (0.80) and `HEADING_OFFSET_DEG`
(180), plus `true_heading()` and `rotation_centre()`. `amiga_nav.py` and
`rover_log.py` both import them; neither defines its own any more.

**The bug this removes.** The two files disagreed on the offset (0.65 vs
0.794), and `rover_log.py` never applied the 180 deg heading offset - it
stepped "back" along the raw receiver heading, which points forward on this
mast. Taught marks sat 1.6 m ahead of the true rotation centre, and a
replayed mission stopped **1.44 m past** each taught spot: more than one
plot pitch. Reproduced from the 27 Oct code in simulation. The controller's
own "1 - 1.5 cm" figure could not reveal it, because it measures against the
same wrong mark.

**Old teach files are repaired on load.** `load_marks_json` ignores the
stored centre and re-derives it from the stored antenna fix and heading with
the current constants. Format-1 files (no `format` key) are read as raw
heading. A note is printed when this moves a mark.

## 2. Averaged, fix-checked teach marks

`rover_log.py` no longer takes one reading per mark. `m` averages 3 s with
the machine stopped and refuses the mark - plot id not used up - unless:

| | |
|---|---|
| every GGA in the window | RTK fixed |
| wheel speed | never above 10 mm/s |
| position scatter | under 2 cm |
| heading scatter | under 0.5 deg |
| readings | at least 3 |

Marks now store the averaged antenna fix, the **true** heading, the scatter,
and the sample count. Summary files carry `"format": 2`. The CSV gains a
`heading_true_deg` column; `heading_deg` stays raw so old analysis still
works.

## 3. GPS faults hold instead of aborting

`Rover.unsafe()` is split into `gps_fault()` (recoverable) and
`hard_fault()` (CAN, Dashboard state). On a GPS fault `drive_loop` holds:
zero speed, AUTO_ACTIVE kept alive at 20 Hz, controller frozen. Once the fix
has been good for 2 s it resumes **the same leg** through
`GotoController.on_resume()`, which keeps the locked approach line and turn
latch and only resets timers. After 90 s it stops cleanly and `--resume`
continues.

Simulated: fix lost for 8 s, 0.6 m short of a plot, mid-deceleration. The
machine held, resumed on the locked line, and stopped 0.9 cm from the mark.

`mission` also checks the fix at the moment of capture and watches it
through the dwell. GPS trouble there marks the plot `flag_gps` and the run
continues.

Per-mark results go to `<teachfile>_run_<UTC>.csv`: stop error along and
across the row, heading error, fix quality, correction age, holds.

## 4. Each mark squares to its taught heading

`load_marks_json` returns the taught heading and `mission` squares to it.
`--heading` is now an override and warns.

Simulated on a 2-row serpentine with headland transits: taught headings give
**zero** in-place rotation inside any plot. The old `--heading 0` gave
170 - 350 deg of rotation at every plot of row 2.

New `amiga_nav.py plan <json>`: prints each leg and flags any mark whose
final turn exceeds 20 deg. On a correctly taught serpentine only the second
headland point is flagged.

  controller can be run from tests and scripts.

## Before the first field run

1. Re-teach. Old files load, but were taught one reading at a time.
2. Teach the real route in the real direction, stopped square to the row.
3. `python3 amiga_nav.py plan <file>` - only headland points flagged.
4. Copy `vehicle.py` to the Pi along with the two programs. Both import it.
