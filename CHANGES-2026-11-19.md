# Changes, 19 Nov 2026

**Capture integration.** The robot drives the plots and the camera app
captures at each one, on one Pi. The camera app is the 18 Sep
`main_app_final.py` with an Autonomous run screen added. Tested end to end
in simulation (the real mission code driving the simulated Amiga, the real
app with fake cameras). It has not yet been driven.

## How it fits together

```
main_app_final.py  (camera app)         amiga_nav.py mission --capture
  Autonomous run screen  ── starts ──>    drives, GPS, CAN at 20 Hz
  CaptureServer  <── Unix socket ──>      CaptureClient
                 /tmp/turf_capture.sock
```

The two stay separate processes on purpose. A Tk redraw or a slow image
write in the app can never delay a CAN frame, and the Dashboard drops out of
auto if it goes ~550 ms without one. The protocol lives in one file,
`capture_link.py`, and both sides import it.

At each plot: stop, square up, settle 1 s, then check the fix and send
`capture R3_C7` with the GPS state. The app points itself at that plot,
using the same `_goto_plot` as the keyboard, so the cameras never restart.
It captures straight away (Automatic) or waits for SPACE / S (Wait for me),
then answers `ok`, `quarantined`, `failed` or `skipped`. The mission keeps
sending zero-speed commands the whole time it waits.

| Answer | Run CSV `result` | What happens |
|---|---|---|
| ok | ok (or flag_gps) | next plot |
| quarantined / failed | flag_capture | next plot; recapture later |
| skipped | skipped | next plot |
| no answer in 30 s (Automatic only) | flag_capture | next plot |
| app closed or crashed | - | **run stops**, machine stopped |
| plot names not in the app's map | - | refused before moving |

## Navigation repo

- **`capture_link.py` (new):** the socket protocol. The mission polls it from
  its control loop and never blocks. The app accepts one mission at a time,
  and a second one is told so at once.
- **`rover_log.py teach --cols N [--start-row R]`:** in this grid mode the
  labels follow the plot map. `n` (`t` from 20 Nov) marks the next plot (R1_C1 … R1_CN, then
  R2_CN … R2_C1, serpentine), `m` marks a headland point (`mark_N`, never
  captured), `s` skips a plot that is not there, and `u` undoes the last
  mark. The name of the next plot is always on screen. Without `--cols`,
  teaching works as before.
- **`amiga_nav.py mission --capture`:**
  - `--capture-mode auto|wait`, `--settle 1.0`, `--capture-timeout 30`.
  - Before moving, it checks every plot name against the app's plot map.
  - It sends live status (driving, arrived, GPS hold, complete) to the app's
    screen.
  - The run CSV gets `capture` and `capture_detail` columns.
  - SIGTERM is handled like Ctrl-C (zero speed, AUTO_READY).
- **`keepalive_wait`:** zero-speed commands while waiting for the app.
- **`test_capture_link.py` (new, 17 tests):**
  - plot naming;
  - the socket;
  - missions against a stand-in app: every plot captured once, headlands
    never; quarantine, skip, a silent app, wait mode, a refused map, no app,
    the app dying mid-run, resume.

## Camera app (separate folder, not in this repo)

- **`autonomy.py` (new):** the Autonomous run screen.
  - Inputs: teach file (newest `~/logs/rover_*.json` by default),
    Automatic / Wait for me, settle, resume.
  - Controls: START RUN, STOP RUN, SKIP PLOT.
  - Shows: live state, counts, and the mission's output.
  - STOP sends SIGINT, which the mission handles like Ctrl-C; SIGTERM
    follows after 3 s if it hasn't stopped.
  - Closing the window stops the run first.
- **`main_app_final.py`:** small hooks, each marked `# AUTONOMY`.
  - An AUTONOMOUS RUN button on the map.
  - No modal dialogs while a run is active (status line and log instead): a
    dialog blocks the app, so the robot would wait on every plot.
  - Arrows, N, P and ESC are locked during a run.
  - SPACE only captures the plot the robot is at.
  - S skips.
  - The GPS fields go into the metadata row.
- **`capture_metadata.py`: schema v5.** 15 `nav_*` columns are appended at the
  end (trigger, run id, teach file, mark, lat/lon, heading, fix, correction
  age, gps_ok, stop error along/cross, heading error, GPS holds). For a hand
  capture they are blank and `nav_trigger = manual`. The file is now
  `<plot>_metadata_v5.csv`.
- **`camera_config.py`: CONFIG_VERSION 1.2.0.**
  - The frame rate is locked at 10 fps (`AcquisitionFrameRateEnable` True,
    `AcquisitionFrameRate` 10.0 ±0.05). Before, it ran free: ~50 fps RGB,
    ~28 fps NIR/red-edge, about 280 MB/s; now about 80 MB/s.
  - Exposure and gain are unchanged.
  - By the config rules this starts a new data series.

## Not yet known

- Whether 10 fps verifies on the real cameras. The rate node can round; if
  the read-back is outside ±0.05 fps every capture is quarantined, and the
  status line says so at once. If that happens, widen
  `TOL_FRAME_RATE_HZ`.
- The whole thing on hardware: cameras and CAN on one Pi, under load.
